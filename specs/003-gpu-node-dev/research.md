## 1. vLLM OpenAI-Compatible API

**Decision**: Use vLLM's built-in OpenAI-compatible server (`vllm.entrypoints.openai.api_server`) and call it from the worker agent via the `openai` Python client or plain `httpx` POST to `http://localhost:8000/v1/chat/completions`.

**Rationale**: vLLM ships a drop-in OpenAI server endpoint. Using it avoids writing a custom inference server; PagedAttention and continuous batching are enabled by default. The `openai` SDK is unnecessary overhead — `httpx.AsyncClient` is sufficient and avoids an extra dependency.

**Alternatives considered**: Directly importing vLLM Python API (LLM class). Rejected — the subprocess-based server model is more robust under concurrent load and easier to monitor independently.

**Key details**:
- Start vLLM: `python -m vllm.entrypoints.openai.api_server --model meta-llama/Llama-3.2-1B --port 9000`
- Worker calls: `POST http://localhost:9000/v1/chat/completions` with `{"model": ..., "messages": [{"role": "user", "content": enriched_prompt}]}`
- Model choice: `meta-llama/Llama-3.2-1B` (≈2.5GB VRAM) or `Qwen/Qwen2.5-0.5B` as fallback if VRAM is tight. Thunder Compute instances typically have 24GB+ VRAM (A100/A10).
- Hugging Face token required for gated models — pass as `HUGGING_FACE_HUB_TOKEN` env var.

## 2. ChromaDB Embedded Setup

**Decision**: Use ChromaDB in embedded (in-process) mode with `chromadb.Client()` (no separate server). Embeddings generated by `sentence-transformers` (`all-MiniLM-L6-v2` model, 22M params, CPU-friendly).

**Rationale**: Knowledge base is static — no writes after startup. Embedded mode avoids a network hop; the embedding model is small enough to run on CPU alongside the GPU worker without meaningful resource contention.

**Alternatives considered**: ChromaDB HTTP server mode. Rejected — adds operational complexity for a static knowledge base.

**Key details**:
- On worker startup: read all `.txt` files from `rag/knowledge_base/`, chunk them (≈500 chars, 50 char overlap), embed with `SentenceTransformer("all-MiniLM-L6-v2")`, upsert into ChromaDB collection named `"knowledge"`.
- Retrieval: `collection.query(query_embeddings=[embed(query)], n_results=3)` → returns top-3 chunks.
- Prompt format: `f"Context:\n{chunks}\n\nQuestion: {query}\n\nAnswer:"`.

## 3. pynvml GPU Metrics Collection

**Decision**: Use `pynvml` directly (not `gputil` wrapper) for fine-grained metrics. Initialize once at startup with `pynvml.nvmlInit()`, get handle with `nvmlDeviceGetHandleByIndex(0)`.

**Rationale**: pynvml gives access to all required metrics in a single library call. It's the official NVIDIA binding.

**Alternatives considered**: `gputil` (wraps pynvml). Rejected — doesn't expose ECC error counts directly.

**Key details**:
```python
import pynvml

def collect_gpu_metrics() -> dict:
    pynvml.nvmlInit()
    handle = pynvml.nvmlDeviceGetHandleByIndex(0)
    util = pynvml.nvmlDeviceGetUtilizationRates(handle)
    mem = pynvml.nvmlDeviceGetMemoryInfo(handle)
    temp = pynvml.nvmlDeviceGetTemperature(handle, pynvml.NVML_TEMPERATURE_GPU)
    try:
        ecc = pynvml.nvmlDeviceGetTotalEccErrors(
            handle, pynvml.NVML_MEMORY_ERROR_TYPE_UNCORRECTED, pynvml.NVML_AGGREGATE_ECC
        )
    except pynvml.NVMLError:
        ecc = 0
    return {
        "gpu_util_pct": util.gpu,
        "vram_used_gb": mem.used / 1e9,
        "vram_total_gb": mem.total / 1e9,
        "gpu_temp_c": temp,
        "ecc_errors": ecc,
    }
```
- Fallback: when `pynvml` is unavailable (dev machine without GPU), return zeros and log a warning. Use `MOCK_GPU=true` env var to enable this.

## 4. Master → Worker Communication via ngrok

**Decision**: Worker receives `MASTER_URL` env var (e.g., `https://abc123.ngrok-free.app`) at startup, self-registers via `POST {MASTER_URL}/workers/register`, then sends heartbeats to `POST {MASTER_URL}/workers/heartbeat` every 2 seconds.

**Rationale**: ngrok gives a stable HTTPS URL for the master even with a dynamic IP. Workers on Thunder Compute reach the master over the internet without VPN.

**Alternatives considered**: Tailscale VPN mesh. Considered but rejected — requires account setup on each Thunder Compute instance; ngrok is one command on the laptop.

**Key details**:
- Run `ngrok http 8000` on the laptop before starting workers.
- Copy the ngrok URL → set as `MASTER_URL` env var when launching worker Docker containers.
- ngrok free tier: 1 tunnel, stable for demo duration.
- The master's `POST /workers/register` response returns `worker_id` (UUID) that the worker uses in all subsequent heartbeats.

## 5. Scheduling Strategy Implementations

**Decision**: All strategies implement a common `select_worker(workers: list[WorkerNode]) -> WorkerNode` interface. The scheduler holds a reference to the currently active strategy instance, swapped atomically via `asyncio.Lock`.

**Rationale**: Strategy pattern enables live switching without restart. Lock prevents race condition on strategy swap during concurrent requests.

**Strategy logic**:

| Strategy | Algorithm |
|---|---|
| `round_robin` | Maintain per-instance index counter; `index % len(workers)` |
| `least_active` | `min(workers, key=lambda w: w.active_requests)` |
| `load_aware` | Weighted score: `0.7 * active_requests_norm + 0.3 * avg_latency_norm`; pick min |
| `lowest_latency` | `min(workers, key=lambda w: w.avg_latency_ms)` (exponential moving average, α=0.2) |
| `gpu_aware` | Score: `0.5 * (1 - gpu_util_pct/100) + 0.5 * (vram_free / vram_total)`; pick max |

Only `HEALTHY` workers are eligible. `DRAINING` and `UNHEALTHY` workers are excluded before strategy selection.

## 6. Prometheus Metrics from FastAPI

**Decision**: Use `prometheus-client` library. Expose metrics at `GET /metrics` via `generate_latest()`. Do not use `prometheus_fastapi_instrumentator` (adds hidden middleware complexity).

**Rationale**: Manual metric definition gives precise control over labels and metric names aligned with the Grafana dashboard.

**Metrics to track**:
```python
from prometheus_client import Counter, Histogram, Gauge

inference_requests_total = Counter("inference_requests_total", "Total inference requests", ["strategy", "worker_id", "status"])
inference_latency_seconds = Histogram("inference_latency_seconds", "End-to-end latency", ["strategy", "worker_id"], buckets=[.1, .25, .5, 1, 2, 5, 10])
worker_gpu_util = Gauge("worker_gpu_util_pct", "GPU utilization %", ["worker_id"])
worker_vram_used = Gauge("worker_vram_used_gb", "VRAM used GB", ["worker_id"])
worker_gpu_temp = Gauge("worker_gpu_temp_c", "GPU temperature C", ["worker_id"])
worker_active_requests = Gauge("worker_active_requests", "Active in-flight requests", ["worker_id"])
worker_status = Gauge("worker_status", "Worker health status (1=HEALTHY, 0.5=DRAINING, 0=UNHEALTHY)", ["worker_id"])
```

## 7. Docker Compose + GPU Passthrough

**Decision**: Master stack uses `docker-compose.yml` (no GPU required). Worker stack uses `docker-compose.worker.yml` with `deploy.resources.reservations.devices` for GPU passthrough.

**Key config**:
```yaml
# docker-compose.worker.yml
services:
  worker-agent:
    image: worker:latest
    environment:
      - MASTER_URL=${MASTER_URL}
      - MOCK_GPU=false
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: all
              capabilities: [gpu]
```

**vLLM runs as a sidecar**: Start vLLM first via `docker run --gpus all vllm/vllm-openai:latest --model meta-llama/Llama-3.2-1B --port 9000`, then start the worker agent pointing to `VLLM_URL=http://localhost:9000`.

## 8. Async HTTP Dispatching from Master

**Decision**: Use `httpx.AsyncClient` (single shared instance, created at startup via FastAPI lifespan) for all master → worker HTTP calls. Set `timeout=30.0` for inference (LLM is slow), `timeout=5.0` for heartbeats.

**Rationale**: A shared `AsyncClient` reuses connection pools. `requests` is synchronous and would block the event loop. `aiohttp` is equally valid but `httpx` API is cleaner and matches the test client API.

**Retry logic**: On worker failure (connection error, 5xx, timeout), retry up to 3 times on different workers. Track retries in the in-flight request object.

## 9. Fault Detection Timing

**Decision**: Health monitor runs as an `asyncio` background task (started in FastAPI lifespan). Checks every 2 seconds. Marks worker `UNHEALTHY` if `last_heartbeat` is more than 6 seconds ago (3 × 2s interval).

**Draining triggers** (checked on each heartbeat receipt):
- `gpu_temp_c > 85` → set status to `DRAINING`
- `ecc_errors > 0` → set status to `DRAINING`
- Return to `HEALTHY` when temp drops below 80°C and ecc_errors == 0

**Recovery**: Workers re-register automatically on restart. The `POST /workers/register` endpoint resets their status to `HEALTHY` and resets their metrics.
