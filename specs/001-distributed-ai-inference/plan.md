# Implementation Plan: Distributed AI Inference Orchestration Platform

**Branch**: `001-distributed-ai-inference` | **Date**: 2026-05-09 | **Spec**: [spec.md](spec.md)

---

## Summary

Build a distributed AI inference serving platform that routes 1000+ concurrent LLM requests across multiple worker laptops on a LAN, each running Ollama locally. The system demonstrates distributed scheduling, fault tolerance, and observability using Python 3.11 + FastAPI for both Master and Worker Agent services, containerized via Docker for easy multi-laptop deployment.

---

## Technical Context

**Language/Version**: Python 3.11  
**Primary Dependencies**: FastAPI, uvicorn, grpcio, grpcio-tools, httpx (async), psutil, prometheus-client, matplotlib, pytest, pytest-asyncio  
**Storage**: In-memory only — asyncio.Queue (task queue), dicts (worker registry, task registry), deque (latency window)  
**Testing**: pytest + pytest-asyncio + httpx (AsyncClient for REST) + grpc testing stubs  
**Target Platform**: Docker containers on LAN laptops (macOS, Windows, Linux); Ollama runs natively on host; Prometheus + Grafana in Docker Compose  
**Project Type**: Multi-service distributed platform (REST gateway + gRPC cluster + observability stack)  
**Performance Goals**: Handle 1000+ concurrent client requests; sustain throughput limited by Ollama inference speed on available hardware  
**Constraints**: LAN-only, no cloud, no paid services; Ollama on host reached via `host.docker.internal:11434` (Mac/Win) or `--network=host` (Linux)  
**Scale/Scope**: 2–5 worker laptops, 1 Master, 100–1000 concurrent users; Prometheus + Grafana on Master machine

## Implementation Phases

### Phase 1: Foundation — Proto + Shared Models + Master gRPC Skeleton

**Goal**: Running Master that accepts worker registration and heartbeats via gRPC; no task dispatch yet.

Deliverables:
- `proto/inference.proto` — full MasterService + WorkerService definitions
- `common/generated/` — compiled Python gRPC stubs (grpcio-tools; compiled in Dockerfile)
- `common/models.py` — Pydantic models for REST layer (InferenceRequest, WorkerRecord, etc.)
- `common/enums.py` — TaskStatus, WorkerStatus
- `master/grpc_server.py` — MasterService servicer: Register, SendHeartbeat, Deregister handlers
- `master/registry.py` — WorkerRegistry with status transitions (healthy/busy/draining/unhealthy/offline)
- `master/health_monitor.py` — background coroutine: checks heartbeat timestamps, marks unhealthy
- `master/routers/monitoring.py` — GET /workers (REST, for operator visibility)
- `master/routers/config.py` — GET /health
- `master/main.py` — starts FastAPI (port 8000) + gRPC server (port 50051) concurrently via asyncio
- `master/Dockerfile`
- `docker-compose.yml` (Master, Prometheus, Grafana services)
- Unit tests: `test_registry.py`, `test_master_grpc.py`

Acceptance: Worker gRPC client calls `Register` → appears in registry; health monitor marks it unhealthy after 15s of no heartbeat.

---

### Phase 2: Worker Agent + Ollama Integration

**Goal**: Worker Agent registers with Master via gRPC, sends heartbeats, serves gRPC Infer calls from Master.

Deliverables:
- `worker/ollama_client.py` — httpx async client: POST `/api/generate`; GET `/` health check
- `worker/metrics_collector.py` — psutil CPU/RAM; `nvidia-smi` GPU (graceful fallback to -1.0)
- `worker/agent.py` — startup: detect LAN IP, check Ollama health, call `MasterService.Register` via gRPC; heartbeat loop calling `MasterService.SendHeartbeat` every 5s
- `worker/grpc_server.py` — WorkerService servicer: Infer (concurrency semaphore + ollama_client call), Health, GetMetrics
- `worker/main.py` — starts gRPC server (port 50052) + minimal FastAPI (port 8001, Prometheus only) + agent startup via asyncio
- `worker/Dockerfile`
- Integration tests: `test_worker_grpc.py` (mock Ollama with respx)

Acceptance: Worker starts → gRPC Register → heartbeats every 5s → Master calls gRPC Infer → Ollama result returned.

---

### Phase 3: Task Queue + Dispatch Engine

**Goal**: Master queues client requests and dispatches them to workers via gRPC asynchronously.

Deliverables:
- `master/task_queue.py` — asyncio.Queue wrapper; task_registry dict; enqueue/dequeue/status updates; retry accounting (max_retries, delay, optional backoff)
- `master/strategies/base.py` — SchedulingStrategy ABC: `select_worker(workers: list[WorkerRecord]) -> WorkerRecord | None`
- `master/strategies/round_robin.py`
- `master/strategies/least_active.py`
- `master/strategies/load_aware.py` — composite score: `active_requests*0.4 + cpu_pct*0.2 + ram_pct*0.2 + avg_latency_norm*0.2`; skips overloaded workers
- `master/strategies/lowest_latency.py`
- `master/scheduler.py` — dispatch loop: dequeue task → `select_worker` → `asyncio.wait_for(WorkerService.Infer(...), timeout)` → update task; handles timeout + retry
- `master/routers/client.py` — POST /infer (enqueues, awaits asyncio.Event completion); GET /tasks/{id}
- `master/routers/config.py` — POST /config/strategy (hot-swap without restart)
- Unit tests: `test_strategies.py`, `test_task_queue.py`

Acceptance: 10 requests submitted → dispatched via gRPC to workers → all results returned → strategy hot-swap works.

---

### Phase 4: Fault Tolerance

**Goal**: Worker failure detected, in-flight tasks retried, system continues operating.

Deliverables:
- `master/health_monitor.py` (enhance) — on marking worker unhealthy: scan task_registry for `assigned|processing` tasks on that worker → status=retrying, retry_count += 1 → re-enqueue
- Task timeout in `master/scheduler.py` — `asyncio.wait_for` catches TimeoutError; updates task + retries or fails
- Graceful draining — `Deregister` gRPC call sets worker draining; scheduler skips draining workers; worker removed after idle timeout
- Recovery — re-registration triggers `WorkerService.Health` gRPC call; worker added back only if healthy
- Integration tests: `test_fault_tolerance.py` — simulate worker disappearing mid-run; verify task retry and system continuity

Acceptance: Kill worker container mid-load-test → Master detects within 15s → tasks retry on remaining workers → all requests resolve.

---

### Phase 5: Prometheus Metrics + Grafana Dashboard

**Goal**: Full observability — Prometheus scraping both Master and Workers; Grafana live dashboard auto-configured from repo.

Deliverables:
- `master/metrics.py` — prometheus-client: Counters (requests_total, failed_total, retry_total), Histograms (request_duration_seconds), Gauges (queue_size, active_tasks, healthy_workers); latency window for p95
- `master/routers/monitoring.py` — GET /metrics (Prometheus text via `prometheus_client.generate_latest`); GET /workers (JSON)
- `worker/metrics.py` — prometheus-client: worker_active_requests gauge, worker_inference_duration histogram, worker_cpu/ram/gpu gauges, worker_ollama_healthy gauge
- `worker/routers/monitoring.py` — GET /metrics (Prometheus text)
- `monitoring/prometheus.yml` — scrape config: `master:8000/metrics` every 5s; file SD `monitoring/targets.json` for workers
- Master writes `monitoring/targets.json` when workers register/deregister (Prometheus file-based service discovery)
- `monitoring/grafana/provisioning/` — auto-provision Prometheus data source + dashboard
- `monitoring/grafana/dashboards/cluster.json` — pre-built Grafana dashboard with all required panels
- `docker-compose.yml` (update) — add Prometheus (port 9090) + Grafana (port 3000) services with volume mounts

Acceptance: Open Grafana at `http://master-ip:3000` → cluster dashboard loads automatically → run load test → all metrics update live → kill worker → dashboard shows failure event.

---

### Phase 6: Load Generator + Benchmarking

**Goal**: Concurrent load simulator and strategy comparison benchmark.

Deliverables:
- `client/load_generator.py` — asyncio + httpx; --users, --burst, --ramp, --query-file flags; per-request latency tracking; summary report (throughput, avg latency, p95, failures)
- `client/queries.txt` — 50+ sample queries of varying lengths
- `benchmark/run.py` — iterates over strategies via POST /config/strategy; runs load_generator for each; collects TaskRecord results; outputs matplotlib comparison charts (throughput, latency CDF, worker utilization bars) + CSV

Acceptance: `benchmark/run.py` runs all 4 strategies → produces `benchmark/results/*.png` + `results.csv`.

## Key Design Decisions (Summary)

| Decision | Choice | Reason |
|----------|--------|--------|
| Client-facing API | FastAPI + uvicorn (REST) | Native async, auto-docs, easy testing |
| Internal cluster protocol | gRPC (grpcio) | Strongly-typed proto contracts, HTTP/2 multiplexing, type-safe at compile time |
| Task queue | asyncio.Queue | No external broker needed for this scope |
| Containerization | Docker; Ollama on host | GPU/Metal doesn't work in Docker on macOS |
| Ollama URL (Docker Mac) | host.docker.internal:11434 | Reaches host Ollama from container |
| Observability | Prometheus + Grafana | Zero custom frontend code; pre-configured dashboard in repo; production-grade |
| Worker discovery (Prometheus) | File-based service discovery | Master writes targets.json; no Consul/etcd needed |
| Scheduling | Strategy pattern (4 implementations) | Pluggable, hot-swappable via API |
| Fault detection | Heartbeat timeout (3× interval) | Handles laptop close, Wi-Fi drop, crash |
| Benchmark visualization | matplotlib | No JS bundler, universally available |
